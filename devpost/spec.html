MYR → KRW
Travel Rate Party

A free-to-run public demo for travelers watching the ringgit-to-won reference rate, reading the news, comparing an uncertain forecast, and coordinating with their party.

DAILY REFERENCE RATE · NOT LIVE DEALER PRICING
THE IDEA IN PLAIN LANGUAGE

A website with a shared notebook

React draws the dashboard, the Bi-Monthly Rate Surveillance tab, and the room. Frankfurter supplies daily reference rates; GDELT supplies links from a rolling three-month news window divided into individual month tabs. The browser uses rate history and a small news score to calculate experimental target-reach chances.

Firebase is the shared notebook for rooms and also hosts the website. Travelers sign in anonymously in the background. The first version uses free plans and reaches connected browsers only.

THE TRADEOFF WE AGREED ON

No paid feed for this demo

Free public data lets the dashboard be shared without an API key or payment card. Rates refresh when a new daily observation is available. A natural crossing alert can happen only after that new value arrives.

Forecasts are experimental; news tone is a rough clue, not a proven measure of currency direction. This is not financial advice.

HOW THE PIECES CONNECT

The data path

ONE TRAVELER'S JOURNEY

Tap a step to see what happens

01 Open dashboard

Browser fetches the daily rate and news. A failed refresh leaves the last value visible with its timestamp and an unavailable message.

02 Inspect the graph

Two EUR-based historical series are aligned and converted: EUR→KRW divided by EUR→MYR gives KRW per RM1. The app draws 14 days and highlights the peak.

02A Browse Bi-Monthly rates

A tab in Rate Surveillance requests and caches a selected completed two-month period labeled 2022–2026, with daily rates, period peak, and selected-day details. In October 2026, the newest period is Aug–Sep 2026.

03 Compare forecast

Historical daily changes are sampled into possible paths. The app estimates how many paths meet the target within each calendar window and displays the uncertainty and news context.

04 Create or join room

Firebase assigns an anonymous member ID. A new six-digit room gets a master and target; friends join by code. Unknown codes show the agreed create-room prompt.

05 Buzz together

Test Alert writes a shared event. When a newly published daily rate reaches the target, connected room members see the same event. Open tabs repeat the buzz every 90 minutes while the rate stays above target.

06 Raise roundtable

Members play Follow, Fold, or Hold. At the deadline, no reply counts as Hold; Follow/Fold decides the target, a tie waits for the raiser, and all Hold prompts a revote.

WHERE DATA LIVES

Room record and privacy boundary

Shared in Firebase

{
  masterUid,
  sharedTarget,
  members: { uid: { name, avatar, connected } },
  alert: { eventId, kind, createdAt, lastRateDate },
  roundtable: { id, proposal, deadline, status, votes }
}

Realtime Database listeners deliver changes to open room members. Rules require anonymous sign-in and validate member paths. Do not leave public writes enabled.

Kept in the browser

  • Last rate and its date
  • Bi-Monthly history cached by selected date range
  • Personal target, nickname, avatar
  • Cached three-month headline links and update time
  • Forecast is recomputed from current inputs

No email/password is needed. Clearing browser data creates a new anonymous identity.

This first version has no trusted custom server enforcing room votes. It is a small public demo, not a tamper-proof production service. Do not put private information in room records.

LIMITS TO SHOW CLEARLY

What can fail, and what the app does

Rate/news unavailable

Keep last successful data and its timestamp, mark it stale, show Refresh, and hide a current forecast.

Room service unavailable

Explain that shared room sync is offline. Solo dashboard remains usable; never pretend the party is synced.

Free quota reached

Show a service-unavailable note. Firebase Spark does not charge overage; service resumes when quota resets unless the owner chooses another plan.

REVIEW CHECK

The plan is ready to inspect

What looks solid

Every behavior in the approved PRD has an implementation home. A single hosted database keeps party sync real, and the free services fit the no-payment constraint.

Limits to keep in view

Daily reference rates change the timing of natural alerts. The forecast is a heuristic that needs examples checked during build. Firebase client-side room rules are not hardened for a production service.
